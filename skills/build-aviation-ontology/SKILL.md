# 构建航空业本体

## 目标

在 Data Platform 内完成一条可追溯、可重复执行的链路：源数据 → ODS → 治理 → 本体实体/关系/规则 → 数据标准与字段血缘 → 平台资产 → 知识库/图谱/报表 → 验收。

把仓库中的实现和当前数据库状态视为事实来源。不要仅生成离线文档；除非用户明确只要文件，否则必须把成果装载到平台并验证页面/API 可访问。

## 输入

执行前解析或确认：

- 源码目录与目标分支；优先使用隔离的 `dev` 工作树。
- 项目名称/编码与项目 ID；不得把历史默认 ID `7` 当作固定值。
- ODS 数据源、运行时 DSN 和平台连接；凭据只通过环境变量或平台密钥字段注入。
- 数据源文件、OpenAPI/API 供应商、机场范围、时间窗口和演示参数。
- 目标本体契约：实体、关系、规则、质量规则及预期产物。
- 是否需要平台落库、知识库同步、动态图谱、报表和浏览器验收。

历史航空 Demo 的默认契约是 5 个实体、3 类关系、2 条规则。只有用户采用该 Demo 时才沿用；新项目应从输入数据和业务问题重新推导。

## 执行原则

1. 先扫描现有源码、迁移、路由、表结构、脚本和已有资产，避免重复造数或平行实现。
2. 先记录基线，再修改。每个故障都保留“入口/API → 服务 → 数据表 → 错误 → 根因 → 修复 → 是否改源码 → 验证证据”。
3. 先建立可复现的失败验收，再做治理；不要用放宽非空、伪造外键、补造天气或静默丢弃记录掩盖问题。
4. 区分固定演示基线与实时 API 数据，防止实时变化破坏演示结果。
5. 所有 SQL/装载脚本应幂等；平台多资产写入应尽量事务化，失败不留半成品。
6. API Key、Token、密码不得出现在代码、SQL、Markdown、JSON、日志或 Git 历史中。
7. 不删除用户文件，不覆盖无关改动，不提交运行缓存或构建中间文件。

## 工作流

### 1. 建立环境和基线

- 通过项目编码/名称从平台 API 或数据库唯一反查项目 ID，并验证当前用户写权限；0 条或多条结果均停止，不猜测。
- 核对分支、提交、工作区状态、运行依赖、端口和数据库健康。
- 运行现有基线测试并记录既有失败；不要把既有 DataX/依赖问题算作本次回归。
- 若从项目包导入，先预检包版本、大小、缺表/缺列、附件和跨环境引用；导入后校验记录数、附件和完整性告警。
- 记录项目 ID、数据源 ID、任务 ID、运行 ID，后续报告不得只写显示名称。

### 2. 数据接入与 ODS

- 为每个源定义目标表、主键/业务唯一键、增量游标、审计字段、原始载荷和幂等写入策略。
- API 接入必须验证真实响应形状、分页、数组路径、过滤器、适配器和异常值。METAR 要兼容 `VRB`、`M`、`6+` 等非数值原始值。
- 对航空 Demo，固定基线与实时天气分表保存；无当前报文机场标记 `NO_CURRENT_REPORT`，不得伪造观测。
- 运行接入任务并核对输入数、过滤数、写入数、拒绝数、运行状态和目标表非空/唯一约束。

### 3. 首轮试跑（RED）

- 在治理前保存首轮质量快照，明确预期失败及实际数值。
- 生成可复查的预检报告：对所有候选主键/业务键统计 NULL、空串和重复；对数值转换、时序、机场代码与关系连接字段统计非法值。只有约束 DDL 所依赖的异常数为 0 才进入治理。
- 至少检查资源注册、标准映射、业务键/重复、实体关系可信度；按项目增加完整性、时序、范围和代码集校验。
- 首轮失败是后续治理证据，不要直接覆盖或删除。

### 4. ODS 治理

- 补齐主键或业务唯一键、增量/审计字段、表与字段注释、责任部门、业务系统和发布状态。
- 原始重复证据保留在 ODS；为消费层建立去重表/视图。
- 建立代码字典、字段采标映射和质量规则。
- 对每项修改运行前后对比，确认未丢行、未错误关联、未破坏来源审计。

### 5. 构建本体与字段血缘

- 从业务问题定义实体标识和核心属性，再定义有明确连接证据的关系。
- 每条关系必须记录主语、宾语、源/目标物理表、源/目标字段、键角色和连接条件。
- 规则区分推理规则与约束规则，并落成可执行 SQL/视图或等价计算。
- 生成机器可读契约与人员可读说明；同一实体、关系、规则在 JSON、Markdown、SQL、模型和图谱中必须一致。
- 详细的历史默认契约与已验证入口见 [reference-workflow.md](references/reference-workflow.md)。

### 6. 装载 Data Platform

- 装载前检查治理 SQL、Bootstrap 和请求头使用同一个项目 ID；若脚本仍硬编码历史 ID，先参数化或明确阻止跨项目执行。
- 在运行参考命令前，仓库级扫描并断言不存在会影响本次执行的历史 `project_id=7`、`X-Project-Id: 7`、裸数据源 ID 等引用。
- 校验平台预置依赖真实存在：ODS 目录、责任部门、业务系统、数据地图数据源、开发数据源和报表数据源。不得假设历史数据库 ID（例如 `7` 或 `15`）仍有效。
- 幂等创建或更新：数据标准/标准数据元、字段标准映射、数据地图资源与字段、逻辑模型、物理模型、字段级关系、质量规则、报表数据集/看板。
- 不得只看装载脚本退出码：ODS 元数据和数据地图资源数必须大于 0；返回的模型模板/实例、数据集和看板 ID 必须可查询。
- 重跑后比较关键资产内容和计数。`upsert` 或“幂等成功”不代表已有模型、SQL、字段或图表已刷新。
- 知识库至少包含术语、规则、经验案例和处置动作；同步后验证解析状态和向量状态。
- 先确认知识库是项目级还是行业全局、目标访问角色和可见范围；记录上传文档 ID，并在有界超时内等待解析与向量状态，失败可安全重试。
- 动态知识图谱应为单文件离线 HTML，覆盖实体、关系、规则、字典和物理字段；支持搜索、筛选、详情与分层/力导向切换。
- 模拟页面应把天气、延误、容量、值勤/休息约束映射到可解释的处置决策。
- PostgreSQL ODS 治理与 MySQL 平台装载不是一个事务。为每阶段保存检查点、重试依据和已写入状态；后段失败时明确报告部分完成范围，不宣称端到端事务回滚。

### 7. 验收（GREEN）

必须以最新运行证据验收：

- 数据：源/目标行数、主键非空、唯一性、增量字段和异常值处理。
- 语义：实体/关系/规则计数与契约一致；每条边端点存在；字段血缘无悬空引用。
- 治理：首轮失败项转绿，且原始证据仍可追溯。
- 平台：页面、API、项目头/项目上下文、模型详情、业务数据检索和报表运行时可访问。
- 报表：校验 SQL 方言、目标 schema 和数据源类型；数据集查询必须实际返回结果，运行时鉴权与项目上下文必须通过。
- 知识库：文档解析成功、向量就绪、关键词可检索、HTML 可在受限沙箱中交互。
- 图谱：机器比对当前语义 JSON 与 HTML 中的节点/边；旧 HTML 与新契约不一致即失败。
- 工程：专项测试、语法检查、前端构建、秘密扫描和 `git diff --check` 通过。

若真实 Oracle/达梦、外部 API 或其他环境不可用，明确标记为跳过或受限验证，不得宣称端到端通过。

以下情况必须判定失败而不是“部分成功”：项目 ID 不一致、ODS 元数据为 0、数据地图资源为 0、关系端点悬空、知识库未同步、报表引用错误数据源、治理脚本因脏数据只执行了一部分。

## 交付格式

结论先行，报告：

1. 项目、分支、提交和运行环境。
2. 输入数据与接入运行结果。
   明确本项目期望计数的来源，不把历史 7 表/89 条当作通用验收值。
3. 治理前失败与治理后结果。
4. 实体、关系、规则、标准数据元、字段映射和数据地图数量。
5. 知识库、图谱、模拟页和报表的文件路径及平台访问路径。
6. 测试、构建、API/浏览器验证证据。
7. 已知限制、跳过项、未提交/未推送状态。

不要输出任何真实密钥或数据库密码。
